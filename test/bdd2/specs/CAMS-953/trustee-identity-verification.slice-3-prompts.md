## Implementation Overview

The Data Verification screen's trustee identity task gets a "Why CAMS needs you" sentence and, for
one-candidate tasks, a "How CAMS read this name" section. Both are read from the trustee-match
pipeline's stored scores and never recompute a comparison. First, the seed data those screens are
tested against is generated by running the real pipeline, replacing hand-written scores.

3. Explanation mapper and accordion rendering
4. Playwright e2e, Playwright a11y and integration-harness coverage

Each task leaves the repo green: tests, lint, typecheck, build.

## Task 1: Findings generator

### Context

CAMS identity tasks (`trustee-match-verification` collection, type `TrusteeMatchVerification` in
`common/src/cams/trustee-match-verification.ts`) store `findings`. That field is the trustee-match
pipeline's serialized state (`TrusteeSerializedState` in
`common/src/cams/trustee-match-pipeline.ts`): `sourceRaw`, `sourceNormalized`, `candidates[]` (each
with `camsRaw`, `scores: ScoreByScorer`, `origin`), `match`, `skip` and `error`.

Every seed currently hand-writes the `scores`. Two hand-derived values were wrong in CAMS-953 Slice
2: street closeness for "301" vs "300 Match Ave" is 2/3, not 0.5. The UI built in Task 3 reads these
scores directly, so seed scores must be the ones the pipeline actually produces.

Constraints:

- dev-tools cannot import backend because of ESM resolution; see the comment at
  `dev-tools/db_scripts/lib/compute-fingerprint.ts:8-10`. The generator therefore runs as a backend
  Vitest test.
- `user-interface/src/lib/testing/mock-api2.ts` ships in the app bundle and must not import faker
  (and so not `MockData`). A plain JSON file is safe for it to import.

### Requirements

1. **Scenario definitions.** Create
   `common/src/cams/test-utilities/trustee-match-findings.scenarios.ts` with plain data only: no
   faker, no backend imports. Each named scenario has a DXTR source record (`DxtrTrusteeParty`) and
   the CAMS trustees that exist in the pool (`Trustee`-shaped, with fixed `trusteeId`s so seeds can
   insert the same trustees). Scenarios:

   | Key                                  | Intended outcome                                                 |
   | ------------------------------------ | ---------------------------------------------------------------- |
   | `noCandidates`                       | no CAMS trustee recalled                                         |
   | `multipleCandidates`                 | 2 candidates, pipeline does not resolve (the `'ambiguous'` case) |
   | `oneCandidateStateDiffers`           | 1 candidate, only `doesStateMatch` fails                         |
   | `oneCandidateAddressAndPhoneDiffer`  | 1 candidate, street/city/zip and phone not exact                 |
   | `oneCandidateNameAddressEmailDiffer` | 1 candidate, name not `exact`, zip and email differ              |
   | `oneCandidateExactName`              | 1 candidate, name `exact`, some other field differs              |
   | `oneCandidateNothingDiffers`         | 1 candidate, nothing differs; see the note below                 |

   Also include every scenario the current seeds need (Task 2 lists them).

   Note on `oneCandidateNothingDiffers`: a single candidate that matches on every field probably
   resolves (`match` non-null), so the pipeline would never create a task for it. If the generator
   produces a match, drop this scenario and record that in the implementation notes. Task 3 covers
   the fallback sentence with a unit test only.

2. **Generator test.** Create
   `backend/lib/use-cases/dataflows/trustee-match-findings.generator.test.ts`. For each scenario it:
   - runs `runTrusteeMatchPipeline(context, source)` from
     `backend/lib/use-cases/dataflows/trustee-match-pipeline-orchestrator.ts`;
   - serializes the result with `serializeState` from `trustee-match-pipeline.ts`;
   - asserts on the outcome: unresolved (`match === null`), no `error`, and the intended candidate
     count;
   - compares the full keyed result to the checked-in file with
     `await expect(JSON.stringify(result, null, 2) + '\n').toMatchFileSnapshot('../../../../common/src/cams/test-utilities/trustee-match-findings.generated.json')`.
   - Regenerate the file with `npm test -- -u trustee-match-findings.generator` in `backend/`. A
     scorer change that alters output fails this test until the file is regenerated.
3. **In-memory trustee pool.** The recall stages call four methods on
   `factory.getTrusteesRepository(context)`: `findTrusteesByName`, `findTrusteesByIds`,
   `searchTrusteesByName` and `searchTrusteesByNameScored`. Stub each with
   `vi.spyOn(MockMongoRepository.prototype, ...)`, following
   `trustee-match-pipeline-orchestrator.test.ts`. Each stub filters the scenario's pool with the
   same predicate the Mongo implementation uses
   (`backend/lib/adapters/gateways/mongo/trustees.mongo.repository.ts:252-340`); read each query and
   mirror it. Returning the whole pool would make every trustee a name match and produce recall
   output the pipeline never would. Only the recall set is approximated; every score is the real
   scorer's output.
4. **Accessor.** Add `getTrusteeMatchScenarioFindings(key)` to `MockData`
   (`common/src/cams/test-utilities/mock-data.ts`). It returns the generated findings for that
   scenario.

## Task 3: Explanation mapper and accordion rendering

### Context

`user-interface/src/data-verification/trustee-verification/TrusteeMatchVerificationAccordion.tsx`
renders a pending identity task. Under the header it currently shows a generic problem statement
(~line 462):

> Trustee sent from the court does not match a CAMS Trustee for {caseLink}

Below that it renders `TrusteeComparisonTable`, built by `buildTrusteeComparison(findings, source)`
in `trustee-comparison.ts`. Each candidate cell's `differs` flag comes from `differingRows(scores)`
in that file. A row differs only when the stored score shows it was compared and did not match
exactly:

- name: `doesNameMatch.quality !== 'exact'`
- phone: `doesPhoneMatch.quality !== 'exact'`
- street: `doesAddressMatch.streetCloseness !== 1`
- city/state/zip/email: `pass === false`

A scorer that wrote no record means "not compared" and never differs.

**Rule (product decision):** the UI never recomputes a comparison. It reads only the pipeline's
stored scores, so the sentence and the table's warning icons always agree. Only a one-candidate task
spells out details; others get one generic sentence.

### Requirements

1. **Mapper.** Add a pure function, in a new `trustee-explanation.ts` beside
   `trustee-comparison.ts`, from `TrusteeSerializedState` to the explanation. It reuses
   `differingRows` (export it from `trustee-comparison.ts`).

   | Candidates | Sentence (before the case list)                                             |
   | ---------- | --------------------------------------------------------------------------- |
   | 0          | `Trustee information sent to CAMS does not match any trustee in CAMS.`      |
   | 2+         | `Trustee information sent to CAMS matches multiple trustees in CAMS.`       |
   | 1          | `Trustee {fields} sent to CAMS {verb} not exactly match a trustee in CAMS.` |

   For 1 candidate:
   - **Groups.** Map the candidate's differing rows to groups: name → `name`; street, city, zip →
     `address`; state → `state`; phone → `phone`; email → `email`. `foundBy` never counts.
   - **Order and joining.** `{fields}` lists the groups present in the fixed order name, address,
     state, phone, email, joined as `a`, `a and b`, `a, b and c` (no serial comma).
   - **Fallback.** With no group present, `{fields}` is `information`.
   - **Verb.** `{verb}` is `does` for one group (or the `information` fallback) and `do` for two or
     more.
   - Examples:
     - address+phone →
       `Trustee address and phone sent to CAMS do not exactly match a trustee in CAMS.`
     - state only → `Trustee state sent to CAMS does not exactly match a trustee in CAMS.`
     - name, zip, email →
       `Trustee name, address and email sent to CAMS do not exactly match a trustee in CAMS.`

   The mapper also returns `showNameInterpretation`. It is true only when there is exactly one
   candidate and that candidate's `scores.doesNameMatch` is missing, failed, or has a `quality`
   other than `'exact'`. That is the same condition as the name row's `differs`, so reuse it.

2. **Sentence rendering.** Replace the problem statement for pending tasks:
   - Render `{sentence} Affects {n} case(s):` followed by the existing case link or links. Singular
     `1 case`, plural `{n} cases`.
   - The case-list span currently prints its own `{n} cases:` prefix (`caseLink`, ~line 315). Remove
     it on this path so the count appears once.
   - Keep the `Loading…` placeholder while detail loads.
   - The sentence needs `findings`, which arrive with the detail fetch. Until detail loads, show
     only the loading placeholder, not the generic sentence.
   - Resolved (approved) tasks keep their current "Trustee X was appointed to…" text.
3. **Name section.** When `showNameInterpretation` is true, render a section with an `<h3>` "How
   CAMS read this name", directly before the "Potential Matches" `<h3>`. Its body is
   `findings.sourceRaw.fullName`, displayed exactly as received. Do not display `sourceNormalized`;
   it is lowercase with punctuation stripped. Give the section a `data-testid`.
4. **Not in this slice:** the ACMS professional id is not displayed anywhere (do not render
   `acmsProfessionalId`), and possible-duplicate candidates get no special marking.

- `user-interface/src/data-verification/trustee-verification/trustee-explanation.ts` (new) and

### Requirements
